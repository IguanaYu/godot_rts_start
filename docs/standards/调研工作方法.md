# 调研工作方法

> **何时查它**：接到任何调研任务（竞品怎么做 / 某技术能不能用 / 某机制有没有发展历史）时，开工前先读本文，按五层结构推进。
> 配套文档：[策划工作流方法论](策划工作流方法论.md)（本文是其中「① 调研」阶段的展开）。

---

## 一、调研五层结构

调研不是"找资料"，是依次回答五个问题。每层回答什么、怎么做、项目内实例：

| 层 | 回答的问题 | 一句话做法 |
|---|---|---|
| 1. 目的层 | 这个任务到底要解决什么问题？ | 拆子问题，明确每问由哪几层回答，**与用户对齐** |
| 2. 现状层 | 我们的家底是什么？ | 代码/设计现状盘点 + 可信度分级 |
| 3. 横向层 | 同类产品怎么做？ | 案例库 → 机制分析（不是产品评测） |
| 4. 纵向层 | 这个设计从哪来、怎么变的？ | 机制级演化史，找 2-3 个关键节点 |
| 5. 结论层 | 所以我们怎么做？ | 三档候选 + 避坑 + 必须有结论 |

### 1. 目的层

开工前先写下：**这个调研要解决什么问题**，拆成哪些子问题，每个子问题由下面哪几层来回答。

- 拆出来的判断标准比资料本身更重要。例：[中立物设计 PVE 视角调研](../research/product/中立物设计_PVE视角调研.md) 开头先立了两个问题——「这个中立物是否产生博弈？是否解决玩家不出基地的问题？」——后面所有案例都拿这两问过滤，无谓的罗列直接被砍掉。
- **必须与用户对齐目的再开工**。目的理解偏了，后面查得越多偏得越远。

### 2. 现状层

先盘家底，再去看别人怎么做。不知道自己有什么，就看不懂别人为什么那样做。

- 盘点代码/系统现状，逐项标注**可信度**（亲测有效 / 推测 / 未验证），防止把"以为的"当"确认的"。
- 实例：[T4阶段设计_调研报告](../plans/T4阶段设计_调研报告.md) 对 8 个维度（AI/胜利条件/难度/重开/引导/配置/音效/美术）做现状盘点，每项标注 [A/B/C] 可信度。

### 3. 横向层

同类产品的机制调研。要点：

- **做机制分析，不做产品评测**。问"这个机制在它那里解决什么问题、代价是什么"，不问"这游戏好不好玩"。
- 案例来源参考 [数据获取来源列表](../manual/数据获取来源列表.md)。
- 实例：[audio_00_overview](../research/technical/audio_00_overview.md) 的「决策矩阵：什么需求 → 用什么」——把 13 个资源站按需求归类，直接可查。

### 4. 纵向层

问这个设计/机制的发展历史：**从哪来、2-3 个关键演化节点为什么变、被淘汰的为什么被淘汰**。还在被新产品使用的，就是经过时间检验的答案。

- 深度做到**机制级演化**即可（找 2-3 个关键节点），不做完整产品代际谱系。
- 与横向层的区别：横向看"现在的玩家各有几个做法"，纵向看"这个做法是怎么变成现在这样的、被放弃的分支死在哪"。
- ⚠️ **待补实例**：本项目尚未按此层做过完整调研，首次实践后将实例补在这里。

### 5. 结论层

调研必须以**可拍板的东西**收尾：

- 三档候选（如 audio_00 的「三档推荐方案」：零成本 / 中等预算 / 商业级），或机制候选菜单。
- 避坑清单 + 风险要点。
- 一句话总结（能一句话说清结论，才算调研完了）。

## 二、通用准则

1. **基于真实信息**（硬要求）：不确定的案例去查证，禁止编造。查不到就写「未查到」，比编一个更有价值。
2. **每案例必带「对本作的启示」**：纯罗列 = 没做调研。案例与本作任务无关时，明确说"与本作无关"并砍掉。
3. **先标杆后扩展**：先看 2-3 个标杆案例形成判断框架，再决定要不要扩大范围。与结论无关的扫描是无效调研（见禁止事项 1）。
4. **必须有结论**：调研以候选 + 建议收尾。明确「不做」也是结论；做完没有任何去向 = 白做。

## 三、禁止事项

1. **无效调研**：范围失控，扫了一堆与结论无关的东西。教训：音效调研扫了 14 个 AI 语音工具，结论只有"ElevenLabs 几乎垄断"一句——无效部分没有服务于结论。先立目的层就能避免。
2. **纯罗列不分析**：案例堆了一屏，没有"对本作的启示"，读者无法据此做任何决策。
3. **调研完无去向**：调研文档没有转化成决策/方案，也没有明确"不做"。教训：中立物、局外成长两份调研完成后断链搁置。

## 四、范例拆解：audio_00 为什么是范本

[audio_00_overview](../research/technical/audio_00_overview.md) 的结构每个环节都服务"读者能直接拍板"：

| 环节 | 它做了什么 | 对应本文 |
|---|---|---|
| 详细报告索引 | 00-06 系列的入口，一页看全 | 五层各层的成果聚合 |
| 决策矩阵 | 「什么需求 → 用什么」直连表 | 横向层的产出形态 |
| 三档推荐方案 | 零成本/中等/商业级，各配代价 | 结论层的三档候选 |
| 风险与合规要点 | 先读坑再动手 | 结论层的避坑 |
| Godot 集成路线图 | 落地步骤 + 代码示例 | 向下游（技术设计）交接 |
| 一句话总结 | 结论压缩成一句 | 结论完整性自检 |

## 五、产出标准与去向

- **存哪**：竞品/玩法调研 → `research/product/`；技术/做法调研 → `research/technical/`。命名「主题_对象_调研」或系列式（`audio_00_overview` 起头，06 收总结）。
- **必须登记** [docs/README.md](../README.md) 对应分区，一行写清「何时查它」。
- **必须有去向**：调研产出 → 进入决策（`decisions/`）或方案（`plans/`），或明确标注「不做，原因 X」。生命周期规则见 README 维护规则。
