# 玩法设计讨论方法论

> 本文整理了一份玩法设计讨论（设计师与设计师、设计师与 AI、设计师与团队）的方法论——核心原则、回答结构、具体技巧、常用术语、检查清单。
>
> 适用于：策略游戏/RTS/RPG 等需要"系统化设计思考"的玩法讨论。不适合：纯创意发想、剧情写作、美术方向。
>
> 本文是 [RTS_资源转化图分析.md](RTS_资源转化图分析.md) 的姊妹篇——前者是**分析工具**，本文是**讨论工具**。

## 引言：什么是好的玩法设计讨论

玩法设计讨论**不是 brainstorming（头脑风暴）**，也**不是 code review（代码评审）**。

它的本质是：**两个人用系统化语言共同推理一个设计决策的取舍**。

- 头脑风暴追求"数量"——多产出想法
- 代码评审追求"对错"——发现 bug 和坏味道
- **玩法设计讨论追求"张力"**——把决策的张力（trade-off）充分展开，让决策者看清每个选项的代价

**好的玩法设计讨论的标志**：
1. **设计师看到了之前没看到的维度**（不是被说服，是被打开）
2. **决策选项的代价被充分呈现**（不是隐藏代价）
3. **最终决策由设计师做出**（讨论者不替设计师拍板）

## 一、核心原则

### 原则 1：用框架而非直觉

每个设计判断都应该能用**框架**解释，而不是"我感觉这样好"。

- ❌ "我觉得图纸建造不好，因为代入感不强"
- ✓ "图纸建造把 Trigger 从主动改成自动，破坏了 1:1 直接对应的体感契约"

**为什么**：框架让讨论可以复盘、可以迁移、可以教学。直觉只能说服已经认同你的人。

### 原则 2：分两面看，不要单边倒

任何设计选择都有**好处**和**代价**。讨论者要做的不是选边，是把两面都呈现给决策者。

```
对任何设计 X：
├── 好的一面（解决了什么问题）
└── 问题的一面（付出了什么代价）
```

**反面例子**：用户提"送兵机制"，我之前一直肯定它好，直到用户主动让我分析问题才发现反模式风险。

**正面例子**：用户问"科技送兵怎么样"，我同时分析"降低难度"和"破坏互惠风险"两面。

### 原则 3：给选项，不给答案

讨论者**永远不要替设计师做决策**。讨论者的工作是**展开选项空间**——把可能的方案、各自的代价、适合的场景呈现出来。

- ❌ "你应该走高警式 UI 路线"
- ✓ "高警式 UI、星际式快捷键、CE2 式全局队列——这三个方向各自的代价是什么，你倾向哪个？"

**为什么**：决策权在设计师。讨论者拍板 = 设计师失去学习机会。

### 原则 4：挑战核心假设

很多设计纠结的根源**不在表层问题，在底层假设**。讨论者要识别并温和地质疑底层假设。

- 用户说"我必须保留操作每个小兵"——这是真的必要吗？还是历史包袱？
- 用户说"我担心代入感不强"——代入感的真正来源是什么？是建筑吗？

**为什么**：底层假设一旦松动，整个决策空间会重新打开。

### 原则 5：用反问推进

每轮讨论**结尾给一个反问**，把球踢回给设计师。反问的作用是：
1. 让设计师聚焦（避免发散）
2. 揭示真实诉求（让设计师自己说出来）
3. 推动决策（强迫做选择）

**好的反问**：聚焦在"你想达到什么"，不是"你想要什么方案"。

- ❌ "你想要方案 A 还是方案 B？"
- ✓ "你担心的'RTS 难'，是 APM 难，还是决策难，还是多线难？"

### 原则 6：承认错误，及时纠正

讨论者会犯错（编造案例、误用框架、错误判断）。**承认错误比坚持错误更有价值**——它建立了信任，让设计师敢于暴露真实想法。

- 我编造了红警送狗的例子 → 用户识破 → 我立刻去搜证 → 基于真实信息重新分析

**反例**：很多 AI 助手坚持错误判断，导致用户失去信任，讨论质量下降。

## 二、回答结构模板

一个好的玩法设计讨论回答，通常包含以下结构（不一定全用，但应该有意识地组织）：

### 模板：5 段式回答

```
1. 复述/确认 —— 把用户的核心问题用自己的话复述一遍，确认理解
2. 框架分析 —— 用资源转化图或其他框架拆解问题
3. 多方案对比 —— 给出 2-4 个方案，用表格对比代价
4. 推荐 + 理由 —— 给出倾向（但不强制），说清楚理由
5. 反问收尾 —— 抛回一个聚焦的问题
```

### 示例：用户问"科技送兵怎么样"

**1. 复述/确认**：
> 你想用"升科技送兵"来降低 RTS 难度，让玩家投资后有即时反馈。

**2. 框架分析**：
> 用资源图看，这是把 E→T 和 E→A 两条边合并成复合边。
> 经典 RTS：E→T（升科技）+ E→P→A（造兵营出兵）
> 你的设计：E→T+A（升科技同时送兵）

**3. 多方案对比**：

| 方案 | 优点 | 代价 |
|---|---|---|
| 每次升级都送 | 决策简单 | 决策同质化 |
| 关键科技送 | 戏剧性突破 | 平时反馈少 |
| 不送 | 经典 RTS 体验 | 投资真空期 |

**4. 推荐 + 理由**：
> 我倾向"关键科技送，水科技不送"——避免反模式但保留价值。

**5. 反问收尾**：
> 你担心的"难"是 APM 难，还是决策难？这决定了该用哪个工具降低难度。

## 三、具体技巧清单

### 技巧 1：用资源转化图术语精准表达

**用途**：避免模糊描述，让设计判断可量化、可对比。

| 模糊表达 | 资源图术语 |
|---|---|
| "这个建筑很有用" | "这个建筑是 P 节点，参与环 2" |
| "这个机制很慢" | "这条边的 Delay 长" |
| "玩家被卡住" | "缺少节奏断点" |
| "雪球不可逆" | "矩阵下半三角全空，没有负面关系" |
| "三个种族不一样" | "三个种族强化不同的环" |

**为什么有用**：术语让讨论从"感觉"升级到"结构"，让所有人对同一现象有共同的描述。

### 技巧 2：用表格做对比

**用途**：把多个方案的差异压缩到一屏内，让决策者一眼看到所有选项。

**模板**：

| 方案 | 维度 1 | 维度 2 | 维度 3 |
|---|---|---|---|
| A | ... | ... | ... |
| B | ... | ... | ... |
| C | ... | ... | ... |

**关键**：列要选**对决策有区分度**的维度。比如对比造兵方案时，"是否破坏兵营价值"是有区分度的，"是否使用数字键"是无区分度的（所有方案都用）。

### 技巧 3：ASCII 图表达系统结构

**用途**：用最简单的字符画出节点关系，比纯文字描述清晰。

```
经典 RTS：
   E ──→ P ──→ A
        ↑
    兵营是必要中转

CE2 式：
   E ──→ A
       ↑
   直接换兵（绕过兵营）
```

**关键**：ASCII 图不要画太复杂，3-5 个节点足够。复杂图应该用表格代替。

### 技巧 4：用"甜区"分析极端选项

**用途**：当选项是连续光谱时，用甜区找中间地带。

**模板**：

```
送的兵战力 ──→ 玩家体验
─────────────────────────────────
0-100       ──→ 没用，玩家忽略
100-500     ──→ 种子部队（甜区）
500-1500    ──→ 缓冲部队
1500+       ──→ 替代产兵（过强）
```

**关键**：甜区分析的本质是**承认极端都有问题**，引导决策者找平衡。

### 技巧 5：引用反模式（Anti-pattern）

**用途**：用经典设计批判支撑判断，比纯个人观点更有说服力。

**反模式库**（持续积累）：

| 反模式 | 来源 | 核心问题 |
|---|---|---|
| 持续生成的免费单位 | SC2 Swarm Host | 破坏互惠风险/回报循环 |
| 数值 buff 型种族差异 | CE2 大多数 Leader | 边际递减，玩起来像同一个游戏 |
| 全正面关系图 | CE2 矩阵 | 雪球不可逆，缺乏翻盘 |
| 投资真空期被填平 | 经典 RTS 的痛点 | 失去"押注"戏剧性 |
| 复杂科技树在短局游戏 | 30+ 节点的科技树 | 玩家没时间体验 |

**关键**：反模式不是"绝对不能用"，是"用了要警惕什么"。每个反模式都有合理使用的场景。

### 技巧 6：节奏对齐分析

**用途**：当游戏有多个周期性系统时（指挥官技能 CD、升本时间、产兵周期），检查它们是否对齐。

**模板**：

```
时间轴：
0s ── 30s ── 60s ── 90s ── 120s

系统 A 周期：[●]      [●]      [●]
系统 B 周期：   [●]       [●]      
                ↑
            是否对齐？错位会怎样？
```

**关键**：节奏错位可能产生**意外的复杂性**（玩家被迫频繁切换心智模式），也可能产生**意外的简单性**（玩家忽略某个系统）。

### 技巧 7：决策密度量化

**用途**：估算玩家在单位时间内的决策数量，判断游戏是否过载。

**模板**：

```
10 分钟游戏的最大决策次数 ≈ 20-30 次
分配：
├── 战斗决策：10-15 次
├── 运营决策：5-8 次
├── 科技决策：2-3 次
└── 战略决策：2-3 次
```

**关键**：决策密度过高 = 玩家疲劳；过低 = 玩家无聊。甜区取决于游戏类型。

### 技巧 8：失败归因清晰度

**用途**：评估某个设计是否让玩家"输得明白"。

**模板**：

| 设计 | 失败归因 | 玩家体验 |
|---|---|---|
| 全手动建造 | "我没补人口" | 清晰，可改进 |
| 全预设建造 | "我选错模板了" | 模糊，难学 |
| 科技送兵过多 | "我升错科技了" | 致命，新手弃游 |

**关键**：好的设计让玩家**输得明白**——能复盘，能改进，能再来一局。

### 技巧 9：因果可见性原则

**用途**：检查游戏事件是否有可见的来源，避免"凭空出现"的感觉。

**模板**：

| 事件 | 来源 | 因果可见性 |
|---|---|---|
| 枪兵出现 | 从兵营走出来 | ✓ 强 |
| 金币到账 | 矿工运回 | ✓ 强 |
| 科技解锁 | 进度条走完 | ✓ 强 |
| 召唤物出现 | 单位身上动画 | ✓ 强 |
| 兵凭空在鼠标位置生成 | 无 | ❌ 切断 |

**关键**：经典 RTS 几乎不违背因果可见性。违背会让玩家本能反感。

### 技巧 10：先承认错误再纠正

**用途**：当讨论者发现自己之前的判断错了（编造、误用、误判），主动承认。

**模板**：

```
1. 承认错误 —— "我之前的判断有误"
2. 说明错在哪 —— "我编造了那些案例"
3. 立即纠正 —— "基于真实信息重新分析"
4. 给新判断 —— "所以现在的结论是..."
```

**为什么**：建立信任比坚持正确更重要。承认错误让讨论更真实。

## 四、常用术语库

### 系统结构术语

| 术语 | 定义 | 例子 |
|---|---|---|
| 节点（Node） | 资源池或修饰器 | E（经济）、A（军力） |
| 边（Link） | 节点之间的转化 | E→A（花钱造兵） |
| 环（Loop） | 共享节点的多条边形成的循环 | 经济自催生环 |
| 主资源池 | E/P/T/A/T2 五个必备节点 | 任何 RTS 都有 |
| 约束器 | 只设 cap 不参与转化的节点 | 人口 S、电力 Power |
| 修饰器 | 修改边/节点属性的元节点 | Info、Energy |

### 关系类型术语

| 术语 | 定义 |
|---|---|
| Convert（转换） | 花掉 A 得到 B |
| Catalyst（催化） | A 加速 B 的产出 |
| Unlock（解锁） | A 是 B 的前置门 |
| Drain（消耗） | A 持续吃掉 B |
| Inhibit（抑制） | A 降低 B 的效率 |
| Decay（衰减） | A 随时间减少 |

### 节点属性术语

| 术语 | 选项 |
|---|---|
| Stock vs Flow | 存量 vs 流量 |
| Bounded vs Unbounded | 有界 vs 无界 |
| Tangible vs Intangible | 有形 vs 无形 |
| Continuous vs Discrete | 连续 vs 离散 |
| Centralized vs Distributed | 集中 vs 分散 |

### 边属性术语

| 术语 | 选项 |
|---|---|
| Delay | 即时/短/中/长 |
| Reversibility | 可逆/不可逆 |
| Rate | 每 tick 转化多少 |
| Efficiency | 转化比例 |
| Trigger | 自动/主动/被动/条件 |
| Determinism | 确定/概率 |

### 四类典型环

| 环 | 名称 | 路径 |
|---|---|---|
| 环 1 | 经济自催生 | E→T2→E |
| 环 2 | 军力-地盘 | E→A→T2→E |
| 环 3 | 人口压力 | A→S→卡兵→补 Depot |
| 环 4 | 科技-军力 | E→T→A 质量→E |

### 设计判断术语

| 术语 | 含义 |
|---|---|
| 反模式（Anti-pattern） | 看似合理但实际有害的设计 |
| 甜区（Sweet spot） | 极端选项之间的最佳平衡点 |
| 投资真空期 | 投资后到回报前的低战力时段 |
| 节奏断点 | 强迫玩家抬头思考的系统时刻 |
| 因果可见性 | 游戏事件是否有可见来源 |
| 决策密度 | 单位时间内的决策数量 |
| 决策同质化 | 多个本应不同的决策趋同 |
| 互惠风险 | 一方能造成威胁但不承担威胁 |

## 五、反例与正例对比

### 反例 1：单边倒的回答

**反例**：
> 用户：图纸建造好不好？
> AI：不好，破坏代入感。

**问题**：没有展开代价，没有给选项，没有挑战假设。

**正例**：
> 用户：图纸建造好不好？
> AI：分两面看。好处是降低操作门槛，代价是切断玩家动作和游戏反馈的 1:1 对应。给你三个方向——全图纸、半图纸、全手动——各自的代价是 X、Y、Z。你倾向哪个？担心代入感的话，具体是担心哪一层？

### 反例 2：用直觉代替框架

**反例**：
> 用户：兵营应该有队列吗？
> AI：应该有，因为没队列兵营就没价值。

**问题**：直觉判断，没解释为什么没价值。

**正例**：
> 用户：兵营应该有队列吗？
> AI：用资源图看，队列改写的是 P→A 边的 Trigger 和 Rate。
> - 无队列：Trigger 主动（每次手动点），Rate 持 1 个订单
> - 有队列：Trigger 主动（一次下多个），Rate 按队列顺序
> 队列是兵营作为"持续产能节点"的必要条件——没队列兵营退化为"单次按钮"，价值塌缩。

### 反例 3：替设计师拍板

**反例**：
> 用户：科技送兵怎么样？
> AI：你应该做关键科技送兵，水科技不送。

**问题**：剥夺决策权，不让设计师思考。

**正例**：
> 用户：科技送兵怎么样？
> AI：分两面看 [展开]。我倾向关键科技送，理由是 X。但你的核心诉求是什么——降低难度？保留张力？加快节奏？不同诉求对应不同方案。

### 反例 4：发散不收敛

**反例**：
> 用户问 A，AI 回答了 A、B、C、D、E 五个方面，每个都展开。

**问题**：用户被信息淹没，反而无法决策。

**正例**：
> 用户问 A，AI 聚焦回答 A，结尾给一个反问把球踢回。如果有相关维度（B），用一句话提示"如果未来想聊 B，可以单独展开"。

## 六、检查清单

回答前问自己：

- [ ] 我理解用户的核心问题了吗？（复述确认）
- [ ] 我用了框架而非直觉吗？（资源图、术语）
- [ ] 我分两面看了吗？（好处 + 代价）
- [ ] 我给选项了吗？（不替用户拍板）
- [ ] 我挑战了底层假设吗？（是否有过时假设）
- [ ] 我用反问收尾了吗？（聚焦下一步）
- [ ] 我承认了不确定/错误吗？（建立信任）
- [ ] 我聚焦了没发散吗？（一次回答一个核心问题）

## 七、特别提示

### 关于 AI 助手的特殊性

如果讨论者是 AI 助手（如本文档场景），有几个额外原则：

1. **不要编造案例**——经典游戏的机制必须基于真实信息。不确定时去搜证。
2. **承认不知道**——比编造更专业。
3. **暴露推理过程**——让设计师看到 AI 的思考路径，方便质疑。
4. **不坚持错误**——用户纠正后立即更新判断。

### 关于设计师的特殊责任

如果讨论者是设计师本人（接收建议的一方），有几个原则：

1. **暴露真实诉求**——不要只问"X 好不好"，要说清楚"我为什么考虑 X"。
2. **挑战 AI 的判断**——不要被动接受，主动质疑。
3. **保留决策权**——AI 给选项，但拍板的是你。
4. **复盘讨论**——结束后回顾哪些判断被验证，哪些被推翻。

### 关于长讨论的管理

跨多轮的长讨论（如本文档的源对话）需要：

1. **阶段性总结**——每隔几轮把结论沉淀成文档，避免遗忘。
2. **承认方向的演化**——设计师的方向会随讨论演化，不要假装一开始就清楚。
3. **回到核心问题**——长讨论容易发散，定期回到"我们到底在解决什么问题"。

---

## 八、本方法论的应用案例

本文档的方法论来自一次具体的设计讨论——关于 RTS 游戏的建造、造兵、科技系统的多轮对话。讨论经历了以下阶段：

1. **初步想法**：用户想做"图纸建造"（造兵工厂自动放 2 兵营 + 2 箭塔）
2. **挑战假设**：用"因果可见性"和"1:1 直接对应"分析，发现图纸破坏 RTS 体感
3. **方向转向**：用户改想"建筑送兵"
4. **反模式警示**：引用 Grubby 批判，分析送兵的反模式风险
5. **甜区分析**：找到"种子部队"甜区——送的兵战力 30-50% 敌人
6. **细节决策**：分别讨论造兵 UI、队列、集结点、科技树
7. **节奏适配**：基于"10 分钟游戏"定位简化科技树
8. **沉淀文档**：把所有结论整合成 [RTS_玩法设计建议.md](RTS_玩法设计建议.md)

**这个过程的特征**：
- 每轮都回到核心诉求（"你想简化什么"）
- 每次方向转向都基于明确的依据（不是凭感觉改方向）
- 每个决策都有正反两面分析
- 最终文档是讨论的自然产物（不是事先规划的）

---

## 总结

**好的玩法设计讨论 = 用框架 + 给选项 + 挑战假设 + 反问推进**。

- 不是说服，是打开
- 不是给答案，是展开代价
- 不是单边倒，是分两面
- 不是替决策，是支持决策

**最终目标**：让设计师看到之前没看到的维度，做出比讨论前更明智的决策。

---

## 附：本方法论的局限

1. **适用于系统化设计**，不适合纯创意发想（剧情、美术、音乐）
2. **适用于有框架的领域**，不适合完全新颖的玩法（没有参考点的创新）
3. **依赖双方都熟悉术语**，跨领域讨论需要先建立共同语言
4. **可能过度结构化**，有些设计直觉比框架更准——知道何时该用框架，何时该信直觉
