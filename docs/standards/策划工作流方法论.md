# 策划工作流方法论

> **何时查它**：开新阶段（如 T5）、设计新系统（如英雄系统）、或任何"从想法到 PR"的策划任务开工前通读；做到某一步时回来查该步的标准。
> **不适用**：数值微调、bug 修复——直接 TODO → 实施，不进门（见裁剪表）。
> 展开文档：调研阶段见 [调研工作方法](调研工作方法.md)；讨论技巧见 [玩法设计讨论方法论](玩法设计讨论方法论.md)。

---

## 一、流水线全景图 + 裁剪表

```
idea.md / TODO.md
      │
      ▼
 第0步 目的澄清 ──→ ① 调研 ──→ ② 决策 ──→ ③ 技术设计 ──→ ④ 实施 ──→ ⑤ 反思
 (与用户对齐)        research/   decisions/   plans/          偏离记录    sessions/
                                                                  +PR验收    +沉淀章节
```

**裁剪表**——任务规模决定走几步，防止方法论变成仪式负担：

| 任务规模 | 例子 | 走几步 |
|---|---|---|
| 阶段级 | 定义 T5、新游戏模式 | 0①②③④⑤ 全走 |
| 系统级 | 特效落地、音效系统 | 0①③④⑤（调研轻量） |
| 单机制 | 升本扩基地、某新建筑 | 0③④⑤（调研 = 查 standards + 定向搜证） |
| 数值微调 / bug | 改个伤害值、修 UI bug | 不进门，TODO 直接实施 |

第 0 步任何任务必过。

## 二、第 0 步：目的澄清

开工前与用户对齐三件事，**没对齐不开工**：

1. 要解决什么问题（不是"要做什么功能"——功能和解决方案会变，问题不变）
2. 做到什么程度算完（验收标准）
3. 明确不做什么（范围边界）

> 为什么必须有这步：目的理解偏了，后面每一步都在放大偏差。宁可开工前多问一轮。

## 三、① 调研

五层结构：**目的层 → 现状层 → 横向层 → 纵向层 → 结论层**。

准则一句话：真实信息不编造、每案例带对本作的启示、先标杆后扩展、必须有结论。

坑（一句话版）：
- **无效调研**——范围失控，扫的与结论无关（音效 14 个 AI 工具教训）
- **断链**——调研完没有结论没有去向，等于白做（中立物/局外成长教训）

**完整方法见 [调研工作方法](调研工作方法.md)。**

## 四、② 决策

### 标准三段式

1. **先言明利弊**——每个候选两面展开（好处/代价），不许单边倒
2. **列出可选做法**——候选库形式呈现
3. **选择题拍板**——把决策转成选项让用户拍板，不出开放题让用户自己想方案

### 编号决策记录

拍板结果当场固化成编号表，实施时有据可查：

| 编号 | 项 | 决策 | 理由 |
|---|---|---|---|
| D1 | … | … | … |

实例：[T1_实施计划](../archived/T1_实施计划.md) 二、决策汇总（D1 起 17 项）；[T3阶段设计_C模块决策稿](../decisions/T3阶段设计_C模块决策稿.md)（🔥 标重大调整、作废内容明确标注）。

### 候选库

未被选中的候选不删，留档到候选库供未来复用。实例：[C模块设计候选库](../decisions/T3阶段设计_C模块设计候选库.md)（4 个设计方向 + 22 个候选方案 + 模板复用场景 + 维护说明）。

### 经济推演（决策验证技法）

拍板前用时间轴推演多种玩家战略路径，验证决策没有把游戏推成单解：

```
时间轴：0:00 → 0:30 → 1:00 → …
路径 A（贪经济）：金币流动 / 建筑状态 / 单位数量 …
路径 B（稳一手）：…
路径 C（激进爆兵）：…
```

每条路径推到关键时点，检查：有没有一条路径明显碾压（= 单解风险）？有没有路径全程被压（= 假选项）？
实例：[T1经济底层改造方案](../archived/T1经济底层改造方案.md) 三种流程推演；[T3阶段设计_A模块经济推演](../archived/T3阶段设计_A模块经济推演.md) 6 种战略路径终态推演。

### 连锁影响表

拍板后立即记录辐射范围（受影响模块 | 影响 | 行动），实例见 C 模块决策稿第七节。

**踩过的坑**：**缺收敛**——列了 37 个候选要素但没排"先做哪 3 个"= 分析瘫痪。调研列得再全，决策阶段必须收敛到可选项。

## 五、③ 技术设计

### 总览文档（决策 → 可实施的桥）

- 把决策稿合并成 PR 时，**对照代码现状逐条修正**，冲突处精确到文件/行号。
- 实例：[T3技术设计_00_总览](../archived/T3技术设计_00_总览.md) 第五节「决策稿与代码现状的修正清单」——决策稿写的接口和实际代码不一致的地方全部列出。

### PR 拆分

每个 PR 四要素：**核心交付 + 预计工时 + 依赖关系 + 验收点**。

- 依赖用文本图标注，标出可并行组：`PR-1 → PR-2 → PR-3`，`（PR-4 与 PR-2 可并行）`
- PR 顺序递增可验证：每个 PR 完成后游戏可跑、可验收（不是攒一大坨才能测）。
- 实例：[T1_实施计划](../archived/T1_实施计划.md) 三、PR 拆分（5 个 PR）；[T2_实施路线图](../archived/T2_实施路线图.md) 三、PR 总览 + 四、依赖关系。

## 六、④ 实施

- 按 PR 顺序执行，每 PR 对照验收点。
- **实施偏离记录**：实际执行与计划的差异，明确标注 `⚠️ 实施偏离（相对原计划）`，写清为什么偏。计划不是不能改，是改了要留痕——事后复盘靠它。
- 实例：[T2_实施路线图](../archived/T2_实施路线图.md) 二、当前进度盘点。

## 七、⑤ 反思

阶段收尾必做：

1. **沉淀**：本阶段验证过的经验写进 standards/（方法论文档）；实例：[T3阶段设计_终局与扩展](../archived/T3阶段设计_终局与扩展.md) 第三章「从 T1/T2 沉淀的方法论」。
2. **给库存一个去向**：阶段攒下的创意/候选，要么转 TODO 排期，要么明确标 ❌ 不做并写原因。不许"写了就死"（教训：兵种创意大全、军功 56 个点子搁置至今）。
3. **纪要**：有沉淀价值的讨论过程存 `sessions/YYYY-MM-DD_主题.md`，只存不改。

## 八、与文档体系的接口

每步产出流向（详细规则见 [docs/README.md](../README.md) 维护规则）：

| 步骤 | 产出 | 去向 |
|---|---|---|
| ① 调研 | 调研报告 | research/product/ 或 technical/ |
| ② 决策 | 决策稿 + 候选库 | decisions/ |
| ③ 技术设计 | 总览 + PR 计划 | plans/ |
| ④ 实施 | 偏离记录（写入 PR 计划文档） | plans/ → 完成后 archived/ |
| ⑤ 反思 | 方法论沉淀 / 纪要 | standards/ / sessions/ |

新文档一律登记 README 索引，一行写清「何时查它」。
