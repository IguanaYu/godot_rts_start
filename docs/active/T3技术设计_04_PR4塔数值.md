## 一、本 PR 目标

按 A 决策稿 Q3 调整塔的数值：

| 项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 基础造价 | 150 金 | **180 金** | 略上调，让前 1-2 座性价比仍明显 |
| 递增造价 | 无 | **每多 1 座 +50 金** | 防塔海（第 3 座 280 / 第 4 座 330 / ...） |
| 攻击范围 | 150 | **220** | 让 1-2 座塔能覆盖关键区域 |
| HP | 150 | **180** | 略提升生存 |
| DMG | 12 | **14** | DPS 8 → 10.8 |
| 攻速（CD） | 1.5s | 1.5s（不动） | 决策稿保持 |

**设计意图**：前 1-2 座塔性价比明显（新手能守住），第 3+ 座性价比骤降（防塔海）。

**为什么两个地方都要改**：

**验证**：搜代码确认 `building_placer.get_current_cost` 优先用哪个。从 PR-4 调研看，[`get_current_cost` L107-118](../../scripts/systems/building_placer.gd#L107)：
```gdscript
var base: int = D.COSTS.get(mode, 0)
var bt: int = D.PLACE_MODE_TO_BUILDING.get(mode, -1)
if bt < 0:
    return base
var stats = BuildingStatsRegistry.get_by_type(bt)
if stats == null or stats.cost_increment <= 0:
```

**关键发现**：base 来自 `D.COSTS`（game_data.gd），递增来自 stats.cost_increment。所以 `cost_override` 字段名可能是用于其他地方（如详情面板显示）。**两个地方都改成 180 是安全做法**。

## 三、机制说明：递增造价如何生效

### 现有流程

```
玩家点建造按钮
  ↓
main._on_place_mode_requested
  ↓
building_placer.check_build_block(place_mode, click_pos)
  ↓ 内部调用 get_current_cost(mode) 计算实际造价
  ↓
金币检查：gold >= get_current_cost(mode)
  ↓ 通过则放置
```

### 现有递增公式

```
actual_cost = base_cost + count_of_same_type * cost_increment
```

例：塔的 base = 180 / cost_increment = 50
- 第 1 座：180 金（count=0）
- 第 2 座：230 金（count=1）
- 第 3 座：280 金（count=2）
- 第 4 座：330 金（count=3）
- 第 5 座：380 金（count=4）

## 六、冲突记录（执行者填写）

实施日期：2026-08-12

### 冲突 1（致命）：正常对局不用 `tower_stats.tres`
文档原方案只改 `tower_stats.tres`，但代码追踪发现：玩家/AI 默认 `balanced` 指挥官（`commander_context.gd:10-11`），`balanced.tres:17` 把塔路由到 `tower_standard_stats.tres`（id=`tower_standard`）。`tower_stats.tres`（id=`tower`）只在 `_fallback_basic_building_id` 兜底路径用到，正常对局走不到。
**处理**：战斗数值（HP/DMG/射程）同时改 `tower_stats.tres` + `tower_standard_stats.tres` 两个文件，数值保持一致。

### 冲突 2（致命）：`get_by_type` 歧义会让递增失效
`building_placer.get_current_cost` 调 `BuildingStatsRegistry.get_by_type(1)` 拿 cost_increment，而 `get_by_type`（`building_stats_registry.gd:41-46`）是字典迭代返回第一个 building_type==1 的。三个 tower .tres 的 building_type 都是 1，文件名字母序下 `tower_heavy` 先加载先入字典 → 很可能返回 `tower_heavy`（cost_increment=0）→ 递增失效。（BARRACKS type=3 有同样隐患，本次不修。）
**处理**：采用方案 A —— cost_increment=50 同时写到 `tower_stats` / `tower_standard` / `tower_heavy` 三张卡，零代码改动保证 `get_by_type(1)` 无论返回哪个都生效。重型塔也吃塔海惩罚（按 building_type 统一计数，合理）。`get_by_type` 根因修复留作独立 refactor。

### 顺手清理（用户决策：一起修）
- **C1 死字段 cost_override**：`tower_heavy_stats.tres` 的 `cost_override=130` 从未被代码读取（`get_current_cost` 走 `D.COSTS` 表）。改成 `-1` 删误导值（不改变行为）。注：让该字段真正生效需改 `get_current_cost` 核心逻辑 + 重新平衡各变体定价，远超本 PR。
- **C2 字段注释**：`building_stats.gd` 的 cost_override 注释标注"当前未生效"。
- **C3 悬停静态价**：`detail_panel.gd:523` `show_temporary_mode` 原用 `D.COSTS.get(mode,0)` 显示静态基础价，与 tooltip 动态价不一致。改为优先 `building_placer.get_current_cost(mode)`，fallback `D.COSTS`。
- **C4 硬编码兜底**：`building.gd:165` `_setup_stats` TOWER 分支 `max_hp=150` 改 180，让编辑器预览/深层兜底与新数值一致（正常运行不走这条，保持一致即可）。
